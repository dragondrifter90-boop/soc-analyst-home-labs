## Scenario and Objective

This lab simulates a harmless Windows service installation. The objective is to
detect service creation using Windows event `4697`, review related process
creation telemetry, and decide whether the activity is authorized.

### Findings

- Baseline query returned multiple `4697` service installation events before
  the LAB-005 simulation.
- All exported baseline events were generated by the machine account
  `<MACHINE_ACCOUNT>`.
- Observed service names included Windows per-user services with suffixes such
  as `_98338`, `_375bad`, and `_aaba3`.
- Examples included `WpnUserService`, `UserDataSvc`, `UnistoreSvc`,
  `OneSyncSvc`, `CDPUserSvc`, `DevicesFlowUserSvc`, and
  `BluetoothUserService`.
- The service file names mostly pointed to expected Windows paths such as
  `C:\Windows\system32\svchost.exe`.
- Baseline finding: event `4697` is useful, but not automatically malicious.
  The analyst must review service name, service path, creating account, and
  surrounding activity.
- LAB-005 generated one `4697` event for service
  `SOC-LAB-005-PersistenceTest`.
- The acting account was `<ACTING_USER>`.
- The affected host was `<TARGET_VM>`.
- The service was configured to run as `LocalSystem`.
- `ServiceStartType` was `3`, meaning manual/demand start.
- `ServiceFileName` pointed to a benign lab command using
  `C:\Windows\System32\cmd.exe` to write a test file under
  `C:\Windows\Temp`.
- Process context query showed the lab command was created with `sc.exe` by
  `<ACTING_USER>`.
- The parent process for the lab `sc.exe create` command was PowerShell ISE:
  `C:\Windows\System32\WindowsPowerShell\v1.0\powershell_ise.exe`.
- Additional `sc.exe` events were observed from the machine account and Azure
  Guest Agent. These were treated as baseline/service-management noise, not
  part of the lab service creation.
- Defender incident 46 displayed three entities: the target host, the lab user,
  and the machine account. The machine account appeared because normal service
  activity occurred in the same rule window.
- Incident-window review showed 21 service-install events:
  19 Windows per-user services, 1 LAB-005 service, and 1 `KslD` service.
- The 19 per-user services used names such as `BluetoothUserService_b6d82`,
  `UserDataSvc_b6d82`, `UnistoreSvc_b6d82`, and `WpnUserService_b6d82`.
  These were created by the machine account and pointed to expected Windows
  paths such as `svchost.exe`.
- The `KslD` service used `system32\drivers\wd\KslD.sys` and was created by
  the machine account. This appears consistent with Microsoft Defender driver
  activity in this lab context.
- The service-start check did not show the LAB-005 service executing its
  configured `cmd.exe` command. The exported process evidence only confirmed
  `sc.exe create` for the lab service.
- Other `cmd.exe` and `sc.exe` events in the service-start check were created
  by the machine account and did not contain the LAB-005 service name or test
  file path.
- The later start attempt generated `4688` for
  `sc.exe start SOC-LAB-005-PersistenceTest` by `<ACTING_USER>`.
- The service start returned Windows error `1053` because `cmd.exe /c echo ...`
  is not a real long-running Windows service process and does not communicate
  service status back to the Service Control Manager.
- Even though the service start returned `1053`, the configured command did
  execute. A `4688` event showed `cmd.exe` launched by `services.exe` under the
  machine account and writing `C:\Windows\Temp\soc-lab-005-service.txt`.
- Cleanup evidence showed `<ACTING_USER>` ran
  `sc.exe delete SOC-LAB-005-PersistenceTest` from PowerShell.
- The cleanup export confirmed service deletion command execution. File removal
  was performed as part of cleanup, but the exported evidence focused on
  process command lines related to the service name and test file.

## Verdict

`Informational, expected activity - Security testing`.

Reason: the service installation behavior was suspicious and correctly
detected, but it was performed intentionally by the lab operator on an
authorized lab VM with a benign command.

## Response and Recovery

- Confirmed the activity was generated by the authorized lab operator.
- Reviewed service name, service file name, start type, and service account.
- Reviewed nearby `4688` process creation events.
- Deleted the lab service.
- Closed the incident as authorized security testing.

## Detection Improvements

Potential tuning:

- Flag services where `ServiceFileName` contains `cmd.exe`, `powershell.exe`,
  `wscript.exe`, `cscript.exe`, or `rundll32.exe`.
- Flag services pointing to user-writable paths such as `Temp`, `Downloads`, or
  user profile directories.
- Tune out Windows per-user service names ending in session-specific suffixes
  after validating they are expected in the environment.
- Consider separating broad baseline service-install rules from higher-signal
  rules that look for suspicious service paths or command interpreters.
- Add allowlists for known software deployment or management tools.
- Add Sysmon or Defender for Endpoint telemetry for richer service and process
  context.

## Lessons Learned

- Event `4697` confirms that a service was installed, but it does not prove by
  itself that the service is malicious.
- Broad service-install rules can generate noisy incidents because Windows
  creates normal per-user services and Defender-related services.
- `4688` process creation context helped prove that PowerShell launched
  `sc.exe create` for the lab service.
- `ServiceAccount` matters. A service configured as `LocalSystem` would be
  high impact if malicious.
- `ServiceStartType` matters. Start type `3` means manual/demand start.
- A service can return start error `1053` but still execute the configured
  command if the binary is not a real Windows service process.
- Cleanup evidence matters. `sc.exe delete` confirmed that the lab service was
  removed.
